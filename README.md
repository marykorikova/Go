# Trip Service

Это учебный сервис для работы с поездками.

Сервис умеет:
* создавать поездку;
* получать поездку по ID;
* завершать поездку;
* проверять работу сервиса и базы данных.

Данные хранятся в PostgreSQL.

## Запуск окружения

Для работы нужны Docker и `tripgoctl`.

Запуск окружения:
```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect
```

После запуска будет создан файл .env с адресом PostgreSQL.


Миграции
В Makefile настроена автозагрузка .env, поэтому переменные окружения подхватываются автоматически.

Применить миграции:

make migrate-up

Посмотреть их состояние:

export $(grep -v '^#' .env | xargs)
goose -dir migrations postgres "$DATABASE_URL" status

(или make migrate-status, если добавишь такую цель в Makefile)

Откатить последнюю миграцию:

make migrate-down

В проекте создаются две таблицы:

trips — поездки;

trip_status_history — история изменения статусов.

Запуск сервиса

make run

Сервис запускается на порту 8080.

Генерация кода

Часть Go-кода генерируется из OpenAPI-контракта.

make generate

Сгенерированный файл:

internal/generated/api.gen.go

Его не нужно изменять вручную.

Переменные окружения

В работе используются:

HTTP_ADDR — адрес HTTP-сервера;

LOG_LEVEL — уровень логирования;

SHUTDOWN_TIMEOUT — время ожидания при остановке;

DATABASE_URL — адрес PostgreSQL;

DATABASE_MAX_CONNS — максимальное число соединений;

DATABASE_MIN_CONNS — минимальное число соединений;

DATABASE_MAX_CONN_LIFETIME — время жизни соединения;

DATABASE_CONNECT_TIMEOUT — таймаут подключения;

DATABASE_QUERY_TIMEOUT — таймаут SQL-запроса.

Пример находится в .env.example.

HTTP-запросы
Проверка работы процесса:

curl -i localhost:8080/health

Проверка доступности базы:

curl -i localhost:8080/ready

Создание поездки:

curl -i -X POST localhost:8080/api/v1/trips \
  -H 'Content-Type: application/json' \
  -d '{
    "user_id": "5cb72c04-7650-45c9-a79b-bcdba0631e0c",
    "driver_id": "8860b315-ec86-42eb-a17c-7c163d721ff5",
    "start_point": {
      "latitude": 59.9398,
      "longitude": 30.3146
    },
    "end_point": {
      "latitude": 59.929,
      "longitude": 30.3626
    },
    "price": 1450
  }'


  Получение поездки:

  curl -i localhost:8080/api/v1/trips/<trip-id>

  Завершение поездки:

  curl -i -X POST \
  localhost:8080/api/v1/trips/<trip-id>/finish

  Решения
Транзакции
Используется уровень изоляции Read Committed (явно задан в TxManager). Создание поездки состоит из двух запросов: запись поездки в trips и запись статуса в trip_status_history. Оба запроса выполняются в одной транзакции. Если один из них завершится с ошибкой, изменения отменятся через ROLLBACK. Если ошибок нет, выполняется COMMIT. Транзакция хранится в context. Repository берёт её оттуда. Если транзакции нет, repository использует обычный пул соединений. Если Do вызывается внутри другого Do, новая транзакция не создаётся.

Один водитель и одна активная поездка
В PostgreSQL создан уникальный индекс:

CREATE UNIQUE INDEX trips_driver_active_idx
ON trips (driver_id)
WHERE status = 'active';

Он запрещает создавать две активные поездки одному водителю. При нарушении индекса PostgreSQL возвращает ошибку 23505. Сервис преобразует её в ответ 409 driver_busy (проверяется по имени констрейнта).

Завершение поездки
Поездка завершается только при статусе active:

WHERE id = $1 AND status = 'active'

Поэтому при двух одновременных запросах поездку завершит только один из них. Второй получит ошибку 409 trip_completed.

Health и Ready
/health проверяет, что процесс сервиса работает. В базу этот запрос не ходит.
/ready проверяет PostgreSQL (делает Ping). Если база остановлена, он возвращает 503.

Остановка сервиса
Сервис обрабатывает SIGINT и SIGTERM. При остановке он перестаёт принимать новые запросы и ждёт завершения текущих запросов. Время ожидания задаётся через SHUTDOWN_TIMEOUT.

Валидация
Тело запроса декодируется с DisallowUnknownFields(). Обязательные поля и диапазоны координат проверяются до бизнес-логики. При ошибке возвращается 400 invalid_request в формате application/problem+json.

## Архитектура

Сервис построен по слоистой архитектуре. Каждый слой отвечает за свою часть работы.

### Схема слоёв

```text
HTTP-запрос
    |
    v
HTTP Handler
    |
    v
Usecase --------> Domain
    |
    v
Repository
    |
    v
PostgreSQL
```

### Слои приложения

- `internal/http/trip` — HTTP-обработчики. Принимают запросы,
  проверяют входные данные, вызывают usecase и формируют HTTP-ответы.
- `internal/usecase/trip` — бизнес-сценарии создания, получения
  и завершения поездок. Управляют последовательностью операций.
- `internal/domain/trip` — доменные правила, статусы и ошибки поездок.
  Не зависит от HTTP и PostgreSQL.
- `internal/repository/trip` — реализация доступа к PostgreSQL.
  Выполняет SQL-запросы.
- `internal/txmanager` — управление транзакциями PostgreSQL.
- `internal/model` — структуры данных, используемые между слоями.

### Зависимости и интерфейсы

HTTP-обработчики зависят от интерфейсов usecase.

Usecase зависит от интерфейсов репозитория и менеджера транзакций,
а не от конкретной реализации PostgreSQL.

Интерфейсы объявляются на стороне потребителя зависимостей.
Это позволяет подменять реализации моками в unit-тестах.

Конкретные реализации создаются и связываются в
`cmd/trip-service/main.go`.

### Наблюдаемость

- `internal/logger` — структурированное логирование через `slog`.
- `internal/http/middleware` — логирование HTTP-запросов.
- `internal/telemetry` — настройка OpenTelemetry для трассировок
  и метрик.
- `deploy/otel/collector.yaml` — конфигурация OpenTelemetry Collector.

Наблюдаемость подключается на уровне HTTP-сервера и не изменяет
доменную бизнес-логику.

## Лабораторная №3 — координаты и проверка активности поездок

### Возможности

- Сохранение координат поездки: `POST /api/v1/trips/{trip_id}/positions`.
- Получение отсортированной истории координат: `GET /api/v1/trips/{trip_id}/positions`.
- Атомарное сохранение позиции и обновление `trips.last_position_at` через `TxManager`.
- Поиск активных поездок без свежих координат непосредственно в SQL.
- Индекс PostgreSQL для ускорения поиска устаревших поездок.
- Фоновый сканер с одним тикером.
- Ограниченная очередь задач с защитой от дублирования.
- Пул из четырёх воркеров.
- Отправка запросов через Push Service.
- Метрики OpenTelemetry.
- Корректная остановка сканера, очереди и воркеров.

### Сохранение координат

Новые позиции сохраняются в таблицу `trip_positions`.

В одной транзакции выполняются добавление позиции и обновление
`trips.last_position_at`. Если приходит позиция со старым временем,
она сохраняется в историю, но не уменьшает время последней позиции.

### Поиск устаревших поездок

Сканер периодически ищет активные поездки, от которых давно
не поступали координаты. Условие устаревания проверяется в SQL.

Завершённые поездки и поездки со свежими координатами исключаются.
Для поиска создан отдельный индекс PostgreSQL.

### Очередь и воркеры

Сканер работает с одним тикером без параллельного выполнения проверок.

Найденные поездки помещаются в ограниченную очередь. Повторные задачи
не дублируются. При заполнении очереди новая задача отбрасывается
без блокировки сканера.

Четыре воркера обрабатывают задачи и обращаются к Push Service.
Повторные запросы по одной поездке ограничиваются интервалом проверки.

### Push Service

Для Push Service используется отдельный HTTP-клиент с настраиваемым
таймаутом. Клиент проверяет HTTP-статусы и закрывает тело ответа.

Взаимодействие вынесено за интерфейс для удобства тестирования.

### Настройки

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `POSITION_STALE_AFTER` | `2m` | Время устаревания координат |
| `POSITION_CHECK_INTERVAL` | `30s` | Интервал проверки поездок |
| `PUSH_HTTP_URL` | пустая строка | URL Push Service |
| `PUSH_REQUEST_TIMEOUT` | `1s` | Таймаут запроса к Push Service |

Интервалы и таймаут должны быть положительными.
При включённом Push Service требуется `PUSH_HTTP_URL`.

### Метрики

- `tripgo.positions.saved` — успешно сохранённые позиции.
- `tripgo.stale_checks` — результаты постановки задач в очередь.
- `tripgo.position_requests.queue.size` — размер очереди.
- `tripgo.position_requests.workers.active` — занятые воркеры.
- `tripgo.position_requests` — результаты запросов.
- `tripgo.position_requests.duration` — длительность запросов.

### Корректная остановка

При SIGINT или SIGTERM сервис прекращает принимать новые HTTP-запросы,
останавливает сканер, закрывает очередь и ожидает завершения воркеров.
После этого останавливается телеметрия.

Общее время ожидания ограничено `SHUTDOWN_TIMEOUT`.

### Тестирование

Все тесты с проверкой гонок данных:

    go test -race ./... -count=2

Интеграционные тесты PostgreSQL:

    TEST_DATABASE_URL="postgres://tripgo_test:tripgo_test_password@127.0.0.1:15432/tripgo_test?sslmode=disable" go test -race -tags=integration ./internal/repository/trip -count=2

Для интеграционных тестов нужна доступная тестовая база PostgreSQL.

### Новые компоненты архитектуры

- `internal/service/positionscanner` — поиск устаревших поездок.
- `internal/service/positionworker` — очередь и пул воркеров.
- `internal/client/push` — HTTP-клиент Push Service.
- `internal/telemetry` — метрики обработки координат и запросов.
